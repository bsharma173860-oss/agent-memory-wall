## 4. CPU-time bound for offload (H5)

### How the steps were aligned

`cpu-time*.csv` log, once per second, the cumulative CPU seconds (user + system) of every process whose command line contains `vllm` or `sglang` (cpu_log2.py), plus the mtime of one results JSON. agent_energy.py writes that JSON (a) right after each step (after the sessions join and `wall_s` is measured), then dumps the timeline file and sleeps a 20 s cooldown before the next step, and (b) once more in `finally` after each variant (engine stopped, 10 s sleep) — plus a last write when the whole script ends. So:

1. Collapse mtime changes less than 5 s apart into one save (a large JSON can be caught mid-write: 1 such double changes in cpu-time.csv, 0 in cpu-time-offload.csv); the save time is the mtime itself, not the logger's sample time.
2. Build the expected save sequence from the JSON (runs in execution order; per run one save per step, then one end-of-variant save; runs that failed at start-up have only the end save) and match observed saves to it from the end backwards, because the main logger started late. Every match is checked: consecutive step saves must be `wall_s` + 20 s + a small overhead apart, an end save 25-120 s after its run's last step. End-of-variant saves are matched and skipped.
3. Each step's window is [save - wall_s, save]; engine CPU in it is interpolated linearly between samples. An upper window adds the measured overhead before the step plus 2 s.

| log / JSON | saves seen | gap-rule violations | steps not observed | overhead between steps s (median, max) | end saves skipped |

| cpu-time.csv / agents.json | 71 | 0 | 1 | 0.32, 0.55 | 12 |
| cpu-time-offload.csv / agents-offload.json | 14 | 0 | 0 | 0.14, 0.18 | 2 |


**Steps that cannot be aligned or measured:** vLLM GPU-only r1 16/30 s (window starts 267 s before the CPU logger started); vLLM GPU-only r1 48/5 s (window starts 93 s before the CPU logger started). Not observed at all: 1 step(s) of the main run whose save happened before the logger started (vLLM GPU-only r1 16/5 s). vLLM offload at 80 GB has no steps (start-up failure). No JSON other than agents.json and agents-offload.json had its mtime logged, so the 160 GB run is aligned by inference (below), and the gate, LFU/SLRU, cliff and seed runs are not aligned.


**Inferred alignment for SGLang 160 GB.** The CPU logger watching agents.json kept running through the extra runs. Each engine stop shows as the cumulative CPU dropping by more than half. Calibrated on the mtime-aligned runs, the stop is seen 20.8 s (vLLM, n=5) / 21.1 s (SGLang, n=6) after the last step's save, and consecutive saves are wall_s + 20 s + 0.27 s apart (median). Each run's saves are placed backwards from its engine stop. Validation where the truth is known from mtimes, applying the same inference to the vLLM 70 GiB run and to every run of the main matrix: vllm: save-time error -1.2 to +1.5 s, CPU-seconds error -2.91% to +0.12% (n=33 steps); sglang: save-time error -0.7 to +0.8 s, CPU-seconds error -0.05% to +0.02% (n=36 steps). Check on the 160 GB steps: during each inferred 20 s cooldown the engine uses 1.01-1.02 busy cores, the same as during the true cooldowns of SGLang runs (1.01-1.02; SGLang's scheduler keeps about one core busy even when idle; vLLM 0.01-0.03). For SGLang this check is weak (its in-step rate is only ~1.05-1.15 cores); the validation above is the real test. 


CPU-seconds are summed from positive increments: the logged sum drops 81 times by more than 0.5 s without an engine restart (an engine subprocess exiting removes its accumulated CPU from the sum); only a fall by more than half is treated as a restart.


Cross-check: the two loggers ran at the same time during the 70 GiB run; per-step CPU-seconds agree within -0.27% to +0.25%.

### Offload vs GPU-only: engine CPU per turn and the energy bound

CPU energy bound = 10 W per busy core x engine CPU-seconds (an upper bound on the engine's CPU energy if a busy core draws at most 10 W; it ignores package/uncore power that would be drawn anyway). 'Extra' = offload minus GPU-only CPU-seconds per turn in the same cell (rounds pooled). The host-memory term is an **assumption**, not a measurement: every recomputed token written to host and every cached token read back, at 262,144 bytes/token and 1 nJ/byte. GPU saved = GPU-only J/turn - offload J/turn. H5 asks for (extra CPU + host memory) < 10% of the GPU saving; the last column is the looser test that charges the offload engine's entire CPU time.
